# Разработка для MAX: бот и mini app

Практическая памятка по разработке проекта для хакатона. Документ собран по официальной документации MAX и актуален на **18 сентября 2026 года**. API и правила платформы меняются, поэтому перед созданием/передачей решения нужно сверить [историю изменений документации](https://dev.max.ru/changelog-docs) и [историю изменений API](https://dev.max.ru/docs-api#changelog).

## 1. Коротко о платформе

В MAX есть два связанных уровня:

- **Чат-бот** — основной канал взаимодействия: сообщения, команды, кнопки, уведомления, статусы и последовательные сценарии.
- **Mini app** — веб-приложение, которое открывается внутри чат-бота и нужно для сложных форм, списков, каталогов, карт, сравнений и другого насыщенного интерфейса.

Mini app не является автономным приложением: оно подключается к чат-боту и работает внутри MAX. Для связи с клиентом MAX используется MAX Bridge.

Рекомендуемая логика выбора:

| Если основной сценарий… | Начинаем с… |
| --- | --- |
| Последовательный: вопрос → выбор → результат/статус | чат-бота |
| Требует большой формы, списка объектов, нескольких экранов или сложной визуализации | mini app, открываемого из бота |
| Сочетает короткое объяснение/уведомление и сложное действие | связки бот + mini app |

Для кейса «Умный город» сначала формулируем один пользовательский сценарий, а потом выбираем интерфейс. Не стоит начинать с mini app только потому, что он выглядит масштабнее.

## 2. Доступ и подготовка

### Профиль разработчика

Официальное подключение к платформе MAX для партнёров доступно юрлицам, ИП и самозанятым — резидентам РФ. Для создания и модерации собственных сервисов обычно нужен верифицированный профиль организации/ИП/самозанятого. Физические лица и нерезиденты пока не проходят такую верификацию.

Основные шаги:

1. Войти на [business.max.ru](https://business.max.ru) или открыть mini app «MAX для бизнеса».
2. Создать профиль организации, ИП или самозанятого.
3. Пройти верификацию.
4. Создать чат-бота, заполнить его карточку и отправить на модерацию.
5. После модерации получить токен и открыть расширенные настройки.

Для хакатона организаторы могут заранее выдать токен. Это позволяет сразу разрабатывать код, но не отменяет проверки статуса бота, доступа к нему и требований к демонстрации.

### Что нужно локально

- Node.js и npm/pnpm/yarn;
- редактор кода и Git;
- мобильное устройство для регистрации/проверки MAX;
- публичный HTTPS-адрес для mini app и production webhook;
- Docker и Docker Compose для воспроизводимого запуска;
- токен MAX только в переменной окружения.

## 3. Архитектура проекта

Минимальная архитектура для нашего проекта:

```text
Пользователь MAX
       |
       | сообщения / кнопки / запуск mini app
       v
Чат-бот MAX <----> MAX API (platform-api2.max.ru)
       |
       +----> backend проекта ----> БД / внешние данные / бизнес-логика
       |
       +----> mini app (HTTPS) <---- MAX Bridge (window.WebApp)
```

Рекомендуем разделять:

- обработку событий MAX;
- бизнес-логику сценария;
- слой данных и интеграций;
- web-клиент mini app;
- конфигурацию и секреты.

Так будет проще показать архитектуру на защите и заменить тестовые данные реальной интеграцией после MVP.

## 4. Общие правила API MAX

### Базовый URL и авторизация

Используйте `https://platform-api2.max.ru`. Старый домен `platform-api.max.ru` не используем.

Токен передаётся только заголовком:

```http
Authorization: <BOT_TOKEN>
```

Передача токена query-параметром больше не поддерживается. Токен никогда не попадает в Git, клиентский JavaScript, логи или презентацию.

Пример проверки токена:

```bash
curl "https://platform-api2.max.ru/me" \
  -H "Authorization: ${BOT_TOKEN}"
```

Сервис возвращает JSON и HTTP-код. Основные коды:

- `200` — успешно;
- `400` — некорректный запрос;
- `401` — ошибка авторизации;
- `404` — ресурс не найден;
- `405` — метод не поддерживается;
- `429` — превышен лимит запросов;
- `503` — сервис временно недоступен.

Текущий ориентир документации — не более **30 запросов в секунду** к API MAX. В коде нужны таймауты, повтор с backoff для временных ошибок и понятная обработка `429/503`.

### События: Webhook и Long Polling

MAX поддерживает два способа получать события:

- **Webhook** — MAX отправляет HTTPS POST на наш endpoint. Это рекомендуемый и production-вариант.
- **Long Polling** (`GET /updates`) — приложение периодически запрашивает события. Подходит для локальной разработки и тестов, но документация не рекомендует его для production из-за ограничений скорости и хранения событий.

Одновременно использовать оба способа нельзя.

Для webhook:

1. Развернуть endpoint, например `POST /max/webhook`, на публичном HTTPS-домене.
2. Настроить подписку через `POST /subscriptions`.
3. Выбрать только нужные `update_types`.
4. Проверить, что endpoint быстро отвечает `2xx`, а тяжёлая обработка уходит в очередь/фон.
5. Для удаления подписки использовать `DELETE /subscriptions`.

Пример регистрации подписки:

```bash
curl -X POST "https://platform-api2.max.ru/subscriptions" \
  -H "Authorization: ${BOT_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.ru/max/webhook",
    "update_types": ["bot_started", "message_created", "message_callback"],
    "secret": "<WEBHOOK_SECRET>"
  }'
```

Секрет webhook не должен совпадать с токеном бота. Если используем поле `secret`, механизм его проверки на сервере реализуем строго по актуальному описанию `POST /subscriptions`.

### Команды и события

Команды бота регистрируются через `PATCH /me/commands`. Для MVP достаточно нескольких явных команд:

- `/start` — приветствие и вход в сценарий;
- `/help` — краткая инструкция;
- `/reset` — сброс состояния сценария;
- доменные команды проекта, если они реально нужны.

Типовые события, которые пригодятся:

- `bot_started` — пользователь начал диалог или перешёл по deep link;
- `message_created` — новое сообщение;
- `message_callback` — нажатие callback-кнопки;
- `message_edited`, `message_removed`;
- `bot_added`, `bot_removed`;
- `user_added`, `user_removed`.

## 5. Разработка чат-бота

### Официальная JavaScript-библиотека

Для TypeScript/JavaScript официальная документация рекомендует пакет `@maxhub/max-bot-api`.

Установка:

```bash
npm install @maxhub/max-bot-api dotenv
```

Минимальный `bot.js`:

```js
import 'dotenv/config';
import { Bot } from '@maxhub/max-bot-api';

const bot = new Bot(process.env.BOT_TOKEN);

bot.command('start', async (ctx) => {
  await ctx.reply(
    'Привет! Выберите действие ниже.',
    // Здесь добавляем inline-клавиатуру проекта.
  );
});

bot.command('help', async (ctx) => {
  await ctx.reply('Помощь: выберите сценарий и следуйте подсказкам.');
});

bot.on('message_created', async (ctx) => {
  // Обрабатываем только обычные сообщения; команды маршрутизируются отдельно.
  // В реальном проекте проверяем тип и текст сообщения до ответа.
});

bot.on('message_callback', async (ctx) => {
  // Разбираем payload callback-кнопки и меняем состояние сценария.
});

bot.start();
```

Запуск:

```bash
BOT_TOKEN="<token>" node bot.js
```

В репозитории должны быть только `.env.example` и фиктивные значения:

```dotenv
BOT_TOKEN=replace_me
WEBHOOK_SECRET=replace_me
APP_BASE_URL=https://example.ru
```

### Сообщения и кнопки

Для основного сценария используем кнопки, а не заставляем пользователя угадывать команды. Поддерживаемые полезные типы кнопок:

- `callback` — отправляет событие `message_callback` с payload;
- `message` — отправляет заранее заданный текст;
- `open_app` — открывает mini app внутри бота;
- `link` — открывает HTTPS-ссылку;
- `request_contact` — запрашивает контакт пользователя;
- `request_geo_location` — запрашивает геолокацию;
- `clipboard` — копирует строку в буфер обмена.

Inline-клавиатура ограничена 210 кнопками в 30 рядов, до 7 кнопок в обычном ряду и до 3 для `link`, `open_app`, `request_geo_location`, `request_contact`. На практике для MVP держим 2–4 понятные кнопки на шаге.

Пример тела сообщения через API:

```json
{
  "text": "Что нужно сделать?",
  "attachments": [
    {
      "type": "inline_keyboard",
      "payload": {
        "buttons": [[
          {"type": "callback", "text": "Создать заявку", "payload": "create_request"},
          {"type": "open_app", "text": "Открыть форму", "url": "https://example.ru/app"}
        ]]
      }
    }
  ]
}
```

Перед использованием точную схему `open_app` проверьте в текущем описании [кнопок API](https://dev.max.ru/docs-api).

Текст можно форматировать в `markdown` или `html`. Для пользовательских данных экранируем разметку и не вставляем непроверенный HTML.

### Вложения

Медиафайлы (`image`, `video`, `audio`, `file`, `share`) сначала загружаются через `POST /uploads`, затем полученный token передаётся в `POST /messages`. Для изображений допускается прямая URL-ссылка. В текущей документации указаны ориентиры: изображение до 50 MB и 7680×7680, видео до 250 MB, аудио до 256 MB/60 минут, файл до 4 GB. Для хакатона используем небольшие файлы и заранее проверяем лимиты.

## 6. Deep links

Deep link позволяет открыть бота и передать контекст.

```text
https://max.ru/<botName>?start=<payload>
```

Для бота `payload` — до 128 символов. Пользователь получает событие `bot_started`, а значение доступно в `Update.payload`.

Не передаём в payload персональные данные, пароли или секреты. Используем короткий одноразовый идентификатор сессии/заявки.

Deep links полезны для:

- QR-кода на объявлении в доме;
- разных источников перехода;
- открытия сценария для конкретной заявки или дома;
- приглашения пользователя сразу в нужный раздел.

## 7. Разработка mini app

### Ограничения и подключение

Mini app:

- работает внутри MAX и привязывается к чат-боту;
- размещается на хостинге по `https://`;
- использует HTML, CSS и JavaScript; React и MAX UI рекомендованы для интерфейса;
- подключается в настройках бота: **Чат-боты → нужный бот → Настройки → URL mini app**;
- URL должен быть валидным `https://`, не длиннее 1024 символов, без пробелов;
- кнопку запуска можно назвать «Открыть», «Старт», «Играть» или оставить без названия.

### MAX Bridge

Подключение в HTML:

```html
<script src="https://st.max.ru/js/max-web-app.js"></script>
```

После загрузки доступен глобальный объект `window.WebApp`.

Минимальная инициализация на клиенте:

```js
const webApp = window.WebApp;

const rawInitData = webApp.initData;          // использовать для серверной проверки
const unsafeUserData = webApp.initDataUnsafe; // только отображение, не доверять
const platform = webApp.platform;
const version = webApp.version;

document.querySelector('#hello').textContent =
  `Пользователь: ${unsafeUserData?.user?.first_name ?? 'гость'}`;
```

`initData` — URL-encoded строка для серверной валидации. `initDataUnsafe` удобен для интерфейса, но не может быть основанием для авторизации или доступа к данным.

Доступные группы возможностей Bridge включают:

- данные запуска и пользователя;
- кнопки интерфейса MAX и кнопку «Назад»;
- открытие ссылок и отправку сообщений;
- локальное и защищённое хранилище устройства;
- геолокацию, контакты и отдельные возможности устройства;
- share-контент через бота.

Проверяем поддержку конкретной функции на iOS, Android, desktop и web: часть методов, например `DeviceStorage`, `SecureStorage`, биометрия и haptic feedback, имеет ограничения по клиентам.

### Серверная проверка initData

Передавать `initDataUnsafe.user.id` напрямую на backend нельзя. Проверяем оригинальную строку `initData` на сервере:

1. Извлечь параметры `WebAppData`/`initData`, убедиться в уникальности ключей.
2. Сохранить исходный `hash` и исключить его из проверяемого набора.
3. URL-decode значения.
4. Отсортировать пары по имени ключа.
5. Собрать `launch_params` через `\n`: `key=value`.
6. Вычислить `secret_key = HMAC-SHA256("WebAppData", BOT_TOKEN)`.
7. Вычислить `hex(HMAC-SHA256(secret_key, launch_params))`.
8. Сравнить результат с исходным `hash`.
9. Проверить свежесть `auth_date`; документация рекомендует интервал около одного часа.

Только после успешной проверки создаём серверную сессию пользователя. Токен бота хранится только на backend.

### Deep link mini app

Для mini app используется:

```text
https://max.ru/<botName>?startapp=<payload>
```

`payload` доступен как `window.WebApp.initDataUnsafe.start_param` и в `initData`. Для mini app документация указывает ограничение payload до 512 символов. Не кладём туда секреты и персональные данные; используем одноразовый или подписанный идентификатор.

### MAX UI

Для React-интерфейса можно использовать официальную библиотеку `@maxhub/max-ui`:

```bash
npm install @maxhub/max-ui
```

Базовое подключение:

```jsx
import { createRoot } from 'react-dom/client';
import { MaxUI } from '@maxhub/max-ui';
import '@maxhub/max-ui/dist/styles.css';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <MaxUI>
    <App />
  </MaxUI>,
);
```

MAX UI учитывает темы и платформы MAX. Для хакатона это снижает риск визуального конфликта с оболочкой мессенджера и ускоряет сборку формы/списка/карточек.

## 8. Связка бот + mini app

Рекомендуемый поток:

1. Пользователь нажимает `/start`.
2. Бот коротко объясняет пользу и задаёт контекст.
3. Бот показывает кнопку `open_app`.
4. Mini app получает `initData`, проверяет её на backend и открывает нужный экран.
5. Пользователь выполняет сложное действие в mini app.
6. Backend сохраняет результат.
7. Бот сообщает статус или отправляет уведомление.

Не делаем mini app отдельным сервисом без бота: это противоречит модели платформы и усложняет проверку основного сценария.

## 9. Backend и интеграции

Backend проекта нужен для:

- хранения состояния сценария и заявок;
- серверной проверки `initData`;
- доступа к БД и внешним API;
- защиты секретов;
- фоновых задач и уведомлений;
- логирования без персональных данных.

Правила интеграций:

- API внешних систем вызываем только с backend;
- таймауты и retries ограничены, чтобы не образовать цикл запросов;
- для недоступного API заранее готовим тестовый режим с явно помеченными данными;
- в README описываем источник, актуальность, территорию и период данных;
- не выдаём предположение LLM за официальную норму/факт;
- разделяем факт, расчёт, рекомендацию и гипотезу.

## 10. HTTPS и VPS

### Что должно быть доступно

- публичный домен или поддомен для mini app;
- HTTPS с сертификатом доверенного центра сертификации;
- endpoint webhook, если используем webhook;
- открытый только необходимый порт (обычно `80/443` через reverse proxy);
- firewall и отдельный непривилегированный пользователь для деплоя.

HTTP, localhost и самоподписанный сертификат не подходят для production webhook и публикации mini app. Для локальной разработки используем Long Polling либо временный HTTPS-туннель, если это разрешено правилами хакатона.

### Минимальный Docker-подход

Репозиторий должен содержать:

```text
Dockerfile
compose.yaml
.dockerignore
.env.example
README.md
```

Сервисы обычно такие:

- `bot` — backend/обработчик событий MAX;
- `web` — собранный mini app или frontend-сервер;
- `db` — только если нужна персистентность;
- `proxy` — reverse proxy и TLS, если не используется внешний ingress.

Пример интерфейса конфигурации:

```dotenv
BOT_TOKEN=replace_me
WEBHOOK_SECRET=replace_me
DATABASE_URL=replace_me
PUBLIC_BASE_URL=https://example.ru
PORT=3000
```

В production секреты передаются через окружение VPS/secret manager. `.env` не копируется в образ и не попадает в Git.

## 11. Безопасность и персональные данные

- Не логируем токены, `initData`, контакты, полные адреса и персональные данные.
- Не используем `initDataUnsafe` для авторизации.
- Проверяем права на сервере, а не только скрываем кнопки в UI.
- Минимизируем сбор данных: запрашиваем только нужные для сценария поля.
- Для тестов используем синтетические дома, заявки и пользователей.
- Не передаём авторизационные данные через deep link.
- Перед публикацией читаем [правила размещения](https://dev.max.ru/docs/legal/rules), [требования к приложениям](https://dev.max.ru/docs/legal/requirements), [типовое пользовательское соглашение](https://dev.max.ru/docs/legal/agreement) и [типовую политику конфиденциальности](https://dev.max.ru/docs/legal/privacy).

Платформа отдельно запрещает использовать API для авторизационных, транзакционных, сервисных и массовых рекламных сообщений, кроме случаев, прямо предусмотренных договором. Поэтому в нашем MVP не строим рассылку и не отправляем одноразовые коды через MAX без подтверждения, что сценарий разрешён.

## 12. Тестирование перед демонстрацией

### Бот

- `/start` запускает сценарий с чистого состояния.
- Повторный `/start` не дублирует заявки и корректно сбрасывает/продолжает сценарий.
- Все callback payload обрабатываются идемпотентно.
- Непонятный текст получает понятный fallback.
- Проверены пустые, слишком длинные и некорректные значения.
- Ошибка внешнего API показывает пользователю понятный статус.
- Webhook отвечает быстро и не падает при повторной доставке события.
- Токен не виден в логах и исходниках.

### Mini app

- Открывается в мобильном, desktop и web-клиенте, если функция заявлена как кроссплатформенная.
- Работает только по HTTPS.
- `initData` проверяется сервером; подделанный hash отклоняется.
- Просроченная сессия отклоняется.
- Кнопка «Назад», загрузка, ошибки и пустые состояния понятны.
- UI не ломается на ширине от 375 px.
- Mini app открывается из бота и возвращает результат в основной сценарий.

### Демонстрация

Должен существовать один короткий путь, который эксперт проходит без пояснений команды:

```text
Старт → выбор проблемы → ввод данных → результат → статус/следующее действие
```
